# Journal — September 2026

## 2026-09-18 — Warehouses / stock rooms speced (M3 prerequisite, before Inventory intake)

Worked through **inventory distribution** for the three business models (individual / multi-store
chain / franchise) with the founder, in Telugu. Conclusion: the existing pieces already cover most
of it — Stock Placement (`stock_locations`) is live, franchise settlement is fully speced, and
constitution §6 already says a godown/warehouse distributes stock the same way for chain (no
settlement) and franchise (settlement on the transfer). The real **gap** is that stock lives
*outside the selling floor* — a backyard, understairs nook, stockroom, or central godown — and
there was no way to name, place, or distribute from that space.

**Decision (founder-led):** model a warehouse as a **first-class, org-owned storage space**, not a
flagged store.

- **New `warehouses`** table (org-owned; `warehouse_type` = backyard/stockroom/godown/other — a
  label, not behaviour).
- **New `warehouse_stores`** link table — many-to-many: one warehouse → many stores, one store →
  many warehouses. A central godown attaches to several stores; a store's own backyard attaches to
  just that store.
- **`stock_locations` relaxed** to belong to a store **or** a warehouse (`store_id` xor
  `warehouse_id`, one-owner check) — the **same** Stock Placement tree (Floor › Section ›
  Zone/Rack) reused inside a warehouse. No second placement system, no new `placement_type`
  (a "shelf" = the existing `rack`; a flat backyard = one `zone`).
- **Two UI entry points**, one underlying table: the org **Stores** page gets a **"New stock
  room"** action + a stock-rooms grid (org-level, attach many stores); the **Store edit** page
  gets a self-managing **"Stock Rooms" card** (create-and-auto-link to that store, for a backyard/
  understairs). The existing `StockPlacementCard` is reused on the warehouse edit page with
  `warehouse_id`.
- **Mapping view + demo creation facility** (founder add-on, same session): a read-only
  **"Stock room map"** panel on the org Stores page shows which warehouses serve which stores
  (every `warehouse_stores` link, one-warehouse-many-stores made visible). And stock rooms become
  a **first-class part of demo-org creation** — each of the three demo pages
  (`demo.{independent,chain,franchise}.tsx`) gets a `StockRoomsSection` with a **"Seed stock
  rooms"** action, a `warehouses.demo.ts` offline-write-through seeder, a per-store stock-room
  line in the demo cards, and the mapping view per demo org. Demo shapes: independent = a
  store-level backyard (1-to-1); chain = a central godown attached to all stores **plus** one
  store with its own backyard (richest mapping); franchise = a franchisor godown attached to the
  franchise stores; plus an unattached "Transit hold" to show the org-wide state.

**Why now, before "Ready for Inventory":** intake places each SKU onto a location; if a SKU can
live in a godown/backyard, intake must pick a warehouse location from day one — adding warehouses
after intake means retrofitting the picker, stock-level keying, and sync order. So warehouses slot
in as an **M3 prerequisite right after Stock Placement**, the same way Stock Placement itself did.

**Why not "godown-as-a-store":** a warehouse is not a retail outlet — no billing/POS/business-model
identity. Its own table keeps the `store_business_model` view clean (a godown can't make an org
look like a "chain") and avoids polluting store lists/POS.

**Known cost (documented, not hidden):** `stock_locations` RLS becomes dual-scope (store-owned rows
stay store-scoped via `has_store_permission`; warehouse-owned rows go org-scoped via
`has_org_permission`); the intake Picker must union a store's own locations with its attached
warehouses'; PUSH_ORDER gains warehouses → links → warehouse-owned locations.

**Deferred (Phase 4, its own spec):** `stock_transfers` (godown → store movement),
goods-received-from-franchisor, and per-location stock quantities — warehouses are the prerequisite
that makes those honest, not part of this build.

## 2026-09-17 — PWA update prompt (home-screen cache fix)

Fixed installed home-screen PWAs serving stale builds indefinitely.

**Root cause:** `vite.config.ts` uses `registerType: "prompt"` and `src/pwa.ts` dispatched a
`sp:sw-update-ready` event when a new build's service worker finished installing — but
**nothing listened for it**. So the new worker sat in `waiting` forever, and a standalone PWA
(which rarely fully closes) kept serving the old precached shell. Confirmed live on prod
before the fix: the deployed SW registration showed `active: true, waiting: true` with no
prompt shown.

**Fix (commit `bde9de6`):**
- New `src/components/UpdatePrompt.tsx` — listens for `sp:sw-update-ready`, shows a
  bottom-anchored toast ("Update available") with an **Update** button that calls the
  plugin's `update()` to activate the waiting worker and reload. Mounted in `src/main.tsx`.
  Styled with existing tokens + `env(safe-area-inset-bottom)` per constitution §6.
- `vercel.json` — added `Cache-Control: max-age=0, must-revalidate` for `/index.html`
  (belt-and-suspenders, matching the existing `/sw.js` rule).

**Not the problem:** asset filenames are already content-hashed (auto cache-bust) and `sw.js`
already revalidates — so no build-number/manual-versioning scheme was needed; the break was
purely the missing update hand-off.

**Verified on prod after deploy:** clean load shows `active: true, waiting: false`; the
shipped bundle carries the listener + UI; firing the event renders the toast (screenshot).

**Note for existing installs:** devices on the old (listener-less) build need **one** manual
unstick (fully close & reopen the PWA, or re-add the icon). After the fixed version is active,
every future deploy surfaces the prompt automatically.

**Open:** the update path is prompt-based by design (offline-first, Dexie writes persist
before reload); revisit if a silent `autoUpdate` is ever wanted.

## 2026-09-13 — Stock Placement (M3) built + demo integration + location colours

Designed and built the **Stock Placement** module — the store-level location system the
Inventory module will place SKUs into (`specs/roadmap/stock-placement.md`, Final v0.4.0).

(owner/manager, the same access as the store edit page), **read on `inventory.read`**.
Soft-delete only; deleting a non-empty container **cascades with a counted confirmation**
("…also removes 2 racks and 1 zone"). Reserved `layout` jsonb for a future visual planogram
(parked in `backlog.md`).

**UI:** a self-managing **Stock Placement card** on the store edit page (between Store details
and Members, like the Members card — instant save, not tied to "Save changes"): collapsible
tree, rack builder with live code-gen + bulk grid, edit, cascade-delete. Only on the *edit*
page — a store must exist first (same as members), so no card on the create page.

**Demo:** placement is defined **per store in the demo creation form** (prefilled + editable,
reusing the card's building blocks), and created on submit via the **real
`createStockLocation` write-through** — so the demo exercises the real code path and shows
immediately. Bandrip (franchise) uses one **brand-standard streetwear layout on every branch**
(mostly hanging zones + a small stockroom rack section), modelled on the real showroom;
independent (Vasavi) = sections + rack grids; chain (Sri Lakshmi) = multi-floor. Each demo
store card shows the placement inline. `hard_delete_organization` purges `stock_locations`.

**Location colours (added same day):** optional palette colour per location — a constrained
token set (`red…slate`, 8), **not hex**, theme-legible and mappable to buyable colored shelf
labels. A reusable **`LocationChip`** (code + colour; colour is an aid, the code is always
shown) plus a swatch **`ColorPicker`**. Colour shows as a dot on the edit-tree rows, a chip in
the demo editor, and — per the founder — the demo store card now renders the full placement as a
**labelled nested tree** (`section: [Sarees] (8)` → `racks: [E-01-01 …]`), colour chips throughout,
so you see what sits inside each container. Demo templates pre-assign brand colours.

**Verified** (browser, as org owner): create-store → edit shows the placement card (empty →

## 2026-09-12 — Deliveries UX: inline transport bumps + stable ordering

Founder tested the Deliveries flow and asked for three fixes, all in the receiving UI (no
schema change):
- **Inline transport buttons on the Deliveries list.** Moving a parcel `pending → in_transit`
  and `in_transit → received` needs no data entry, so forcing a click into the detail page and
  back was pure friction. Each list row now shows a one-tap button for exactly those two steps
  (**🚚 Mark in transit** / **📦 Mark received**); `received`/`verified`/`ready_for_inventory`
  show none and still open the detail page (Verify needs the line-level check, Approve needs the
  summary). The button `preventDefault`/`stopPropagation`s so it advances in place without
  following the row's link.
- **Shared advance helper.** Extracted `advanceReceiving(invoice, memberId)` into `receiving.ts`
  — writes the stage patch through Dexie (offline-first) and logs the trip activity. Both the
  list (inline) and `DeliveryDetailPage` (`advance()`, keeping its all-items-checked verify
  gate) now call it, so the two paths can't drift.
- **Stable list ordering.** The list sorted by stage then `last_modified_at`, so bumping a
  parcel's status made its row jump. Now sorts by `invoice_date` ascending (oldest first),
  supplier name as tiebreaker, missing dates last — order no longer depends on status.
- **Check-items no longer reorder on edit.** The detail page's check list sorted by
  `last_modified_at`, so editing a row's received qty bumped its timestamp and shoved it to the
  bottom. Line items have no `created_at`/line-number and `_localId` is a random UUID, so we now
  freeze each item's position the first time it's seen (initial timestamp order, remembered in a
  ref) and sort by that frozen index.

**Decisions:** inline advance limited to the two no-data transport steps; `received` rows stay
button-less (open to Verify); ordering keyed on `invoice_date` since there's no `created_at` on
`purchase_invoices`/`purchase_invoice_items`.
**Verified:** drove the full pipeline end-to-end in the demo (pending → in transit → received →
verified → ready-for-inventory) — inline bumps advance without reordering, the check-items fix
holds, and Burrabazar (invoice 08-11) stayed above Metro (08-12) through every status change.
`pnpm typecheck` + `pnpm lint` clean.
**Files:** `receiving.ts`, `pages/DeliveriesPage.tsx`, `pages/DeliveryDetailPage.tsx`.
**Open:** if a permanent, DB-backed line order is wanted, add a `line_no`/`sort_order` column to
`purchase_invoice_items` (the ref-based freeze is per-page-visit only).

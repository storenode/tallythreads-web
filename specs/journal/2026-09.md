## 2026-09-12 — Deliveries UX: inline transport bumps + stable ordering

Founder tested the Deliveries flow and asked for three fixes, all in the receiving UI (no
schema change):
- **Inline transport buttons on the Deliveries list.** Moving a parcel `pending → in_transit`
  and `in_transit → received` needs no data entry, so forcing a click into the detail page and
  back was pure friction. Each list row now shows a one-tap button for exactly those two steps
  (**🚚 Mark in transit** / **📦 Mark received**); `received`/`verified`/`ready_for_inventory`
  show none and still open the detail page (Verify needs the line-level check, Approve needs the
  summary). The button `preventDefault`/`stopPropagation`s so it advances in place without
  following the row's link.
- **Shared advance helper.** Extracted `advanceReceiving(invoice, memberId)` into `receiving.ts`
  — writes the stage patch through Dexie (offline-first) and logs the trip activity. Both the
  list (inline) and `DeliveryDetailPage` (`advance()`, keeping its all-items-checked verify
  gate) now call it, so the two paths can't drift.
- **Stable list ordering.** The list sorted by stage then `last_modified_at`, so bumping a
  parcel's status made its row jump. Now sorts by `invoice_date` ascending (oldest first),
  supplier name as tiebreaker, missing dates last — order no longer depends on status.
- **Check-items no longer reorder on edit.** The detail page's check list sorted by
  `last_modified_at`, so editing a row's received qty bumped its timestamp and shoved it to the
  bottom. Line items have no `created_at`/line-number and `_localId` is a random UUID, so we now
  freeze each item's position the first time it's seen (initial timestamp order, remembered in a
  ref) and sort by that frozen index.

**Decisions:** inline advance limited to the two no-data transport steps; `received` rows stay
button-less (open to Verify); ordering keyed on `invoice_date` since there's no `created_at` on
`purchase_invoices`/`purchase_invoice_items`.
**Verified:** drove the full pipeline end-to-end in the demo (pending → in transit → received →
verified → ready-for-inventory) — inline bumps advance without reordering, the check-items fix
holds, and Burrabazar (invoice 08-11) stayed above Metro (08-12) through every status change.
`pnpm typecheck` + `pnpm lint` clean.
**Files:** `receiving.ts`, `pages/DeliveriesPage.tsx`, `pages/DeliveryDetailPage.tsx`.
**Open:** if a permanent, DB-backed line order is wanted, add a `line_no`/`sort_order` column to
`purchase_invoice_items` (the ref-based freeze is per-page-visit only).

## What this is

StoreParda is a billing/inventory app for independent cloth stores. Before this task,
the app had no public-facing page at all — opening it dropped you straight into the
internal shop-management screens (billing, stock, trips, reports, settings), which
only makes sense for someone already signed in.

This task adds a **marketing landing page** — what a visitor sees when they open
StoreParda before signing in. It explains what the product does, why a cloth-store
owner would want it, and offers a "Sign in with Google" button to get started. Think
of it as the public front door; the actual store-management app is a separate area
behind it.

It does **not** include a working Google sign-in — clicking the button doesn't
authenticate anyone yet (see Scope below).

## Scope

**Included:**
- A new page at the site root (`/`) — brand, one-line pitch, a headline explaining
  the product, a grid of feature highlights, a "why choose us" section, a call-to-
  action banner, and a footer
- A visible "Sign in with Google" button (UI only, see below)
- Light/dark theme, switchable by the visitor, remembered on their next visit
- A navigation bar that starts see-through over the hero image and becomes a solid
  bar once the visitor scrolls down
- A moving/layered background effect behind the headline (parallax)
- The app's real brand logo, shown in the navbar, the hero, and the footer
- Mobile-friendly layout (tested down to a 375px-wide phone screen)

**Explicitly not included (deferred to a later task, M1):**
- Actual Google authentication — no session gets created, no user account gets
  signed in. Clicking the button currently just logs a message to the browser
  console. Wiring up real Google OAuth is scoped to module M1 (see the project
  constitution, `specs/constitution.md`, §5).
- Any logic that detects whether a visitor is already signed in and skips this page
  for them. That requires the real auth system from M1; right now the portal page
  and the internal app are just two separate URLs (`/` vs `/app/...`), not connected
  by any login check yet.

## What a reader needs to know to picture it

- The internal store-management app (billing, stock, etc.) moved from the site root
  to `/app/...` (e.g. `/app/bill`) so it's a clearly separate section from this new
  public page at `/`.
- The app already has a brand mark (a storefront icon in green `#2FBF71` and
  lavender `#7B7FE0`) and a script-style wordmark ("StoreParda"). This task is the
  first place that mark and wordmark actually appear together in the running app.
- The app supports a light theme and a dark theme. A visitor can toggle between them
  with a button in the navbar; their choice is remembered (stored in the browser),
  and if they've never chosen, it follows their device's system setting.

## Changelog

- **v1.2.0** — Fixed the logo showing a visible white square behind it in dark mode.
  The existing PWA icon file (`public/pwa-512x512.png`) has a solid white background
  by design (required for installable-app icons), which looked wrong once it was
  reused inside the page itself. Added `public/logo-mark.svg`, the same artwork with
  no background, and switched the navbar/hero/footer to use that instead. The PWA
  icon files themselves were not changed.
- **v1.1.0** — Replaced the text-only "StoreParda" wordmark in the navbar and footer
  with the actual brand logo image, via a new shared `Logo` component. Added a large
  logo badge above the hero headline.
- **v1.0.0** — Initial implementation: portal page, navbar, hero with parallax
  background, features and selling-points sections, CTA banner, footer, light/dark
  theme, Google Sign-In UI stub, route split between `/` and `/app/*`.

## Verified

`pnpm typecheck`, `pnpm lint`, `pnpm build`, `pnpm test:cov` all pass (91.3% `src/lib`
coverage, unaffected by this change). Manually driven with Playwright against the dev
server: screenshots taken at desktop and 375px mobile widths, in both light and dark
theme, confirming — no horizontal scroll, the sign-in button correctly hidden from the
mobile navbar (a Tailwind class-conflict bug was caught and fixed this way), the
navbar's scroll-triggered transition, the `/app/bill` route still working, and the
logo rendering with no background box in dark mode. Zero browser console errors in any
of these passes.

## Notes

- This inserts ahead of M1 in the roadmap because the portal is the first thing any
  visitor sees, before any auth flow exists.
- Fonts load from Google's CDN, which is a soft break from offline-first purism for the
  *public* portal specifically (the authenticated `/app` shell doesn't depend on it).
  Self-hosting the font files is a reasonable follow-up if that matters before launch.
